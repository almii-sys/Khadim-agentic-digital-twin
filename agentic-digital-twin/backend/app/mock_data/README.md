# Mock Institutional DB — AI Agentic Digital Twin (FYP)

A fully synthetic database that mirrors the shape of a real CMS/SAP + LMS
student-lifecycle system, for developing/testing the Digital Twin without
any production data access. **No real student, faculty, or institutional
data is used anywhere** — every row is generated by Faker or sampled from
realistic distributions.

## Files
- `models.py` — SQLAlchemy schema covering all 6 project modules:
  1. Admissions & Program Exploration → `Program`, `AdmissionApplication`
  2. Academics & University Life → `Department`, `Faculty`, `Course`, `Semester`, `Enrollment`
  3. Degree Progress & Academic Standing → `AcademicStanding`
  4. Research & Thesis Journey → `Thesis`, `ThesisMilestone`
  5. Degree Completion & Graduation → `GraduationClearance`
  6. Forms & Documents → `DocumentRequest`
- `seed.py` — populates the schema with realistic fake data (Faker), preserving
  referential integrity and realistic distributions (grade bell-curves, MS/PhD
  ratio, status mix, etc.)

## Setup
```bash
pip install sqlalchemy faker
python seed.py --reset
```
This creates `twin_mock.db` (SQLite) with:
- 4 departments, 6 programs (MS + PhD)
- 40 faculty (some flagged as PhD supervisors)
- 500 students across programs, statuses, and semesters
- Enrollments, GPA/academic-standing history, thesis + milestone records,
  graduation clearances, document requests, and 150 admission applications

## Adjusting scale/shape
Edit the constants at the top of `seed.py`:
- `N_STUDENTS`, `N_FACULTY` — dataset size
- `MS_PHD_SPLIT` — proportion PhD vs MS (currently weighted 3:1 MS:PhD in the
  program sampling — tune the `weights=` list in `build()` if you want a
  different ratio)
- `DEPARTMENTS` / `COURSE_TITLES` — swap in your actual department and course
  names once you have them, without touching the schema

## Switching from SQLite to Postgres/MySQL
Change `DB_PATH` in `seed.py`, e.g.:
```python
DB_PATH = "postgresql://user:pass@localhost/twin_mock"
```
SQLAlchemy handles the rest — no model changes needed.

## Adding the UniTime-shaped scheduling data
`unitime_models.py` + `unitime_seed.py` add a second mock DB (`unitime_mock.db`)
modeled on UniTime's actual domain concepts (Academic Session → Subject Area →
Instructional Offering → Class → Assignment, plus Student Class Enrollment).
It cross-references the same SAP IDs and course codes from `twin_mock.db`, so
the two mock systems agree with each other the way a real CMS+UniTime
integration would.

```bash
python seed.py --reset            # build twin_mock.db first
python unitime_seed.py --reset    # then build unitime_mock.db from it
```

Note: table/column names here reflect UniTime's well-documented domain model,
not a verified byte-for-byte copy of its internal Hibernate schema (that lives
in UniTime's Java source at github.com/UniTime/unitime — worth checking there
directly if your supervisor wants an exact match). Since timetabling itself is
out of scope for your app, this exists only so other modules can display a
student's schedule/room/timing without live UniTime API access.

## Making it look even more like your real SAP instance
Once you get real field names/ID formats from your coordinator (see prior
guidance — sanitized schema/ERD only, never real rows), just rename the
relevant columns and adjust ID formats (`sap_id` patterns, program codes) —
the relationships and seeding logic stay the same.
